# Supabase schema and offline-sync draft

This is an implementation design, not an applied migration. The project instructions say database schema changes must be made through Lovable, and generated Supabase types must not be edited by hand.

## 1. Design goals

1. Postgres remains authoritative for points, completions, redemptions, and account ownership.
2. Every user action is represented by a replayable command with a stable client-generated ID.
3. Retrying after a timeout is safe: a command executes at most once from the user’s perspective.
4. Offline UI can be responsive, but it must distinguish pending local state from server-confirmed state.
5. Realtime accelerates convergence while connected; reconnect always performs a pull sync because events can be missed.
6. Account linking, especially anonymous-to-existing-account linking, is an explicit migration step rather than an accidental merge.

## 2. Existing logical model

The current project already has the important base entities:

- `goals`: mutable user-owned definitions.
- `completion_records`: check-in history, including `undone_at`.
- `rewards`: mutable user-owned definitions, archived rather than deleted.
- `point_transactions`: append-only ledger, with optional `completion_id` and `reward_id`.
- RPCs: `check_in`, `undo_check_in`, `redeem_reward`, and `get_balance`.

The proposed additions below make retries and incremental sync safe. They should be reviewed and applied through Lovable, not copied directly into `supabase/migrations/` in this repository.

## 3. Server-side schema additions

### 3.1 Timestamps and versions for mutable rows

`goals` and `rewards` currently have `created_at` but no visible update version. Add:

```sql
alter table public.goals
  add column if not exists updated_at timestamptz not null default now(),
  add column if not exists version bigint not null default 1;

alter table public.rewards
  add column if not exists updated_at timestamptz not null default now(),
  add column if not exists version bigint not null default 1;

alter table public.completion_records
  add column if not exists updated_at timestamptz not null default now(),
  add column if not exists version bigint not null default 1;
```

Use a `before update` trigger to set `updated_at = now()` and increment `version`. The trigger should not be applied to `point_transactions`: that table is append-only by project rule.

If the product needs a reliable pull cursor, use a server-generated monotonically increasing change sequence rather than relying only on timestamps. A simple approach is a per-project sequence plus a `change_seq bigint` column on syncable tables, assigned on insert/update. Timestamps remain useful for display and debugging but are not a perfect cursor under clock skew or equal timestamps.

### 3.2 Business uniqueness constraints

The exact policy for re-checking after undo should be decided first. If an undone check-in may be performed again on the same local date, a partial unique index allows one active completion while retaining old undone history:

```sql
create unique index if not exists completion_one_active_per_goal_day
  on public.completion_records (user_id, goal_id, completed_on)
  where undone_at is null;
```

If the intended rule is “a goal can only ever be checked once per date, even after undo,” use a full unique constraint instead and have undo restore/reuse the original row. Do not leave this to client-side checks.

Recommended ledger checks:

```sql
alter table public.point_transactions
  add constraint point_transaction_kind_check
  check (kind in ('earn', 'reversal', 'redeem'));

alter table public.point_transactions
  add constraint point_transaction_amount_check
  check (
    (kind = 'earn' and amount > 0)
    or (kind = 'reversal' and amount < 0)
    or (kind = 'redeem' and amount < 0)
  );
```

Preserve the existing trigger/function controls that make `point_transactions` append-only and restrict writes to `check_in`, `undo_check_in`, and `redeem_reward`.

### 3.3 Idempotency receipt table

Add a small server table to remember completed commands. The operation ID is generated by the client and is never reused for a different command.

```sql
create table public.mutation_receipts (
  user_id uuid not null references auth.users(id) on delete cascade,
  operation_id uuid not null,
  operation_kind text not null check (
    operation_kind in ('check_in', 'undo_check_in', 'redeem_reward',
                       'create_goal', 'update_goal', 'archive_goal',
                       'create_reward', 'update_reward', 'archive_reward')
  ),
  request_hash text not null,
  status text not null check (status in ('succeeded', 'rejected')),
  result jsonb,
  error_code text,
  error_message text,
  created_at timestamptz not null default now(),
  primary key (user_id, operation_id)
);

create index mutation_receipts_created_at_idx
  on public.mutation_receipts (user_id, created_at desc);
```

Recommended retention is at least longer than the maximum expected offline period, for example 30–90 days. A cleanup job can remove older receipts only after that window. If an old command is retried after receipt deletion, the underlying business uniqueness constraints must still make the operation safe.

RLS should allow a user to read their own receipts if the client needs to display command history, but normal clients should not insert, update, or delete receipts directly. The RPCs insert receipts using `security definer` functions with a fixed `search_path` and explicit authorization checks.

### 3.4 Optional change feed table

For a robust pull sync, add a compact per-user change feed rather than querying every table by timestamp:

```sql
create table public.sync_changes (
  change_seq bigint generated always as identity primary key,
  user_id uuid not null references auth.users(id) on delete cascade,
  entity_type text not null check (entity_type in ('goal', 'reward', 'completion', 'transaction')),
  entity_id uuid not null,
  operation text not null check (operation in ('upsert', 'delete')),
  changed_at timestamptz not null default now()
);

create index sync_changes_user_cursor_idx
  on public.sync_changes (user_id, change_seq);
```

Use triggers or the same trusted RPCs to append changes. Do not expose an unbounded public feed. Provide a function such as:

```text
pull_changes(p_after_seq bigint, p_limit int)
  returns { next_seq, has_more, goals[], rewards[], completions[], transactions[] }
```

For a first release, a simpler `pull_snapshot` RPC for the current user is acceptable because this app’s data volume is small. Add cursors before history becomes large.

## 4. RPC contract changes

The three business mutations should accept an operation ID:

```text
check_in(
  p_goal_id uuid,
  p_date date,
  p_operation_id uuid
) returns { completion_id uuid, transaction_id uuid, applied boolean }

undo_check_in(
  p_goal_id uuid,
  p_date date,
  p_operation_id uuid
) returns { completion_id uuid, transaction_id uuid, applied boolean }

redeem_reward(
  p_reward_id uuid,
  p_operation_id uuid
) returns { transaction_id uuid, applied boolean }
```

`applied = false` means the receipt already existed and its stored result was returned. It is not an error.

Each RPC should follow this transaction pattern:

```text
begin

1. Authenticate from auth.uid(); reject unauthenticated calls.
2. Validate the operation ID and request fields.
3. Compute a canonical request hash from operation kind + normalized arguments.
4. Look up (auth.uid(), operation_id) in mutation_receipts.
   - If found with the same request_hash, return its stored result/error.
   - If found with a different hash, reject as operation_id_reused.
5. Lock the relevant goal/reward/completion rows with FOR UPDATE.
6. Enforce the business rule:
   - check_in: one active completion for user + goal + date.
   - undo: target the user’s active completion and append exactly one reversal.
   - redeem: lock the reward and calculate the ledger balance in the same transaction.
7. Insert/update the domain rows and append the ledger row where applicable.
8. Insert a succeeded or rejected mutation_receipt.
9. Commit and return the stored result.
```

Do not implement idempotency by first asking the client whether a request already ran. The receipt lookup and business mutation must be in the same database transaction.

For goal/reward CRUD, prefer client-generated UUIDs for creates and an RPC such as `save_goal(p_operation_id, p_goal_id, p_patch, p_expected_version)`. The expected version gives a clean conflict response instead of silently overwriting another device’s edit. Archives remain updates (`archived = true`), never deletes.

## 5. Browser local storage model

Use IndexedDB, preferably behind a small repository module. React Query should remain the rendered cache; IndexedDB is the durable offline cache and outbox.

Suggested stores:

```ts
type CachedEntity = {
  userId: string;
  entityId: string;
  entityType: "goal" | "reward" | "completion" | "transaction";
  value: unknown;
  serverSeq?: number;
  updatedAt: string;
  pendingOperationIds: string[];
};

type OutboxCommand = {
  operationId: string; // UUID; stable across retries
  userId: string;      // anonymous or permanent auth user at enqueue time
  kind:
    | "check_in" | "undo_check_in" | "redeem_reward"
    | "create_goal" | "update_goal" | "archive_goal"
    | "create_reward" | "update_reward" | "archive_reward";
  payload: Record<string, unknown>;
  requestHash: string;
  createdAt: string;
  attemptCount: number;
  nextAttemptAt: string;
  state: "pending" | "running" | "succeeded" | "rejected";
  lastErrorCode?: string;
  lastErrorMessage?: string;
};

type SyncState = {
  userId: string;
  cursor: number;
  lastFullSyncAt?: string;
  lastOnlineAt?: string;
};
```

Use one IndexedDB database per browser origin. Scope every record by `userId`; on sign-out, clear or quarantine the old user’s cache and outbox. Never let a newly-created anonymous session read another session’s local records.

Persist only what is needed for the app. Do not put Supabase refresh tokens into the outbox payload. Supabase Auth owns session persistence; the queue waits for a valid session before sending.

## 6. Queue lifecycle

### Enqueue

All writes go through one command function, whether the network is currently available or not:

```ts
async function enqueueCommand(
  kind: OutboxCommand["kind"],
  payload: Record<string, unknown>,
): Promise<string> {
  const session = await requireSession();
  const operationId = crypto.randomUUID();
  const requestHash = await sha256(canonicalJson({ kind, payload }));

  await db.outbox.put({
    operationId,
    userId: session.user.id,
    kind,
    payload,
    requestHash,
    createdAt: new Date().toISOString(),
    attemptCount: 0,
    nextAttemptAt: new Date().toISOString(),
    state: "pending",
  });

  // Apply a clearly marked optimistic overlay, then try immediately.
  markPendingInReactQuery(operationId, kind, payload);
  void drainOutbox();
  return operationId;
}
```

For check-in, the optimistic overlay can show the completion as `pending` and provisionally show the expected points. It must not rewrite the authoritative balance as if the ledger had already committed. On failure, remove the overlay and show the server error.

### Drain

Run the drain on app start, after auth is ready, on `online`, on visibility regain, and after enqueue. Use a single per-user mutex so two tabs do not process the same queue concurrently. If multi-tab support is required, use `BroadcastChannel` plus a lease record with an expiry; do not assume an in-memory mutex spans tabs.

```ts
async function drainOutbox() {
  if (!navigator.onLine || drainLock.isHeld()) return;
  return drainLock.runExclusive(async () => {
    const session = await supabase.auth.getSession();
    if (!session.data.session) return;

    for (;;) {
      const command = await db.outbox.nextReady(session.data.session.user.id);
      if (!command) return;

      await db.outbox.markRunning(command.operationId);
      try {
        const result = await sendCommand(command);
        await db.outbox.markSucceeded(command.operationId, result);
        await applyServerResultAndInvalidate(result, command);
      } catch (error) {
        const classified = classifySyncError(error);
        if (classified.kind === "transient") {
          await db.outbox.reschedule(
            command.operationId,
            backoffWithJitter(command.attemptCount),
            classified.message,
          );
          return;
        }
        await db.outbox.markRejected(command.operationId, classified.code, classified.message);
        await removeOptimisticOverlay(command.operationId);
        await refreshAuthoritativeQueries(command);
      }
    }
  });
}
```

Use exponential backoff with jitter for network errors, 5xx responses, token-refresh races, and rate limits. Do not endlessly retry validation errors, insufficient balance, archived goals/rewards, duplicate active check-ins, or version conflicts.

### Sending a command

Keep the mapping from queue command to RPC in one place:

```ts
async function sendCommand(c: OutboxCommand) {
  switch (c.kind) {
    case "check_in":
      return callRpc("check_in", {
        p_goal_id: c.payload.goalId,
        p_date: c.payload.date,
        p_operation_id: c.operationId,
      });
    case "undo_check_in":
      return callRpc("undo_check_in", {
        p_goal_id: c.payload.goalId,
        p_date: c.payload.date,
        p_operation_id: c.operationId,
      });
    case "redeem_reward":
      return callRpc("redeem_reward", {
        p_reward_id: c.payload.rewardId,
        p_operation_id: c.operationId,
      });
    default:
      return callCrudRpc(c);
  }
}
```

The current `useCheckIn` and `useRedeem` hooks should eventually enqueue commands rather than call RPCs directly. Their success/error toasts should be based on command state: “Saved” after server confirmation, and “Waiting for connection” while pending.

## 7. Pull sync and Realtime

On each authenticated app start or reconnect:

1. Drain pending commands first, or mark the UI as having pending local writes.
2. Call `pull_changes(cursor)` until `has_more` is false.
3. Upsert returned server rows into IndexedDB.
4. Advance the cursor only after the page is durably stored.
5. Invalidate or update the related React Query keys.
6. Subscribe to Realtime for the current user’s tables. Realtime events should trigger a targeted pull/invalidation, not bypass the outbox or directly overwrite pending local entities.

If a pull detects that a pending optimistic entity has a conflicting server version, resolve by command type:

- `check_in`: trust the server result; duplicate active check-ins collapse to one completion.
- `undo_check_in`: trust the server’s current `undone_at` state; report already-undone as a resolved no-op if the desired state is achieved.
- `redeem_reward`: never merge balances locally; display success or the authoritative insufficient-balance rejection.
- goal/reward edit: compare `expected_version`; show a conflict and let the user reload/overwrite intentionally.

## 8. Anonymous-to-permanent account transition

The queue must be bound to the current Supabase user ID. When the user links an anonymous account using `updateUser`, the Supabase user ID normally remains the same. Treat that as a continuity-preserving transition and keep the queue.

If the user instead signs into a different existing account:

1. Stop the drain.
2. Export or summarize pending anonymous commands.
3. Ask whether to discard them, retry them against the existing account where valid, or merge local settings manually.
4. Never replay commands carrying the old anonymous `userId` against the new account.
5. Clear the old account’s IndexedDB partition after the decision.

## 9. Minimal rollout sequence

1. Add the `operation_id` and idempotency receipt design to the three business RPCs.
2. Add the active-completion uniqueness rule and test check-in, retry, concurrent check-in, undo, and redemption races in Postgres.
3. Implement an IndexedDB repository and queue without optimistic UI; use it first as a durable retry layer.
4. Route current React Query mutations through the queue and refresh authoritative queries after each result.
5. Add optimistic pending overlays only after failure and account-switch behavior are tested.
6. Add cursor-based pull sync; use Realtime as an accelerator, not as the only consistency mechanism.
7. Add version-checked goal/reward edits if multi-device editing becomes common.

## 10. Important non-goals

- Do not sync or upload a client-computed points balance.
- Do not make `point_transactions` directly writable from the browser.
- Do not treat a successful local optimistic update as a committed redemption.
- Do not use wall-clock timestamps alone as a reliable change cursor.
- Do not silently merge anonymous progress into an unrelated existing account.
- Do not edit generated `src/integrations/supabase/types.ts` by hand; regenerate it after Lovable applies the schema.
